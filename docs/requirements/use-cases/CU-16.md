# CU-16 — Notificar riesgo crítico

**Versión:** 0.1
**Estado:** Borrador en refinamiento
**Clasificación:** Caso de uso funcional candidato
**Fuente:** `CU-03`, `CU-04`, `SRC-11`, requisitos de notificación

## 1. Objetivo

Entregar una notificación a los destinatarios autorizados cuando una predicción y las reglas operativas determinen una condición crítica, registrando el resultado de la entrega.

## 2. Actores

- **Actor iniciador lógico:** `CU-03 Generar predicciones de riesgo`.
- **Actor secundario:** `EXT-03 Servicio de correo/notificaciones`.
- **Destinatarios:** `ACT-02 Farmacéutico`, `ACT-05 Administrador de farmacia` u otros autorizados.

La condición crítica es detectada por reglas del sistema; el servicio de correo es externo.

## 3. Disparador

`CU-03` identifica una condición que cumple la regla de notificación crítica.

## 4. Precondiciones

- Existe una predicción registrada.
- La clasificación operativa es crítica.
- El destinatario está configurado y autorizado.
- El canal está disponible o se puede registrar el fallo.
- La plantilla de notificación está versionada.

## 5. Postcondiciones

### Éxito

- Se genera una notificación con referencia a la alerta.
- Se registra destinatario, canal, fecha y resultado.
- La alerta queda marcada como notificada o pendiente de confirmación, según política.

### Fallo

- Se registra el fallo de entrega.
- La alerta no se marca como entregada.
- Se aplica el mecanismo de reintento o escalamiento aprobado.

## 6. Flujo básico

1. `CU-03` identifica una condición crítica.
2. El sistema crea o recupera la alerta correspondiente.
3. El sistema identifica destinatarios autorizados.
4. El sistema genera el contenido con medicamento, centro, prioridad, fecha y referencia.
5. El sistema envía la notificación mediante `EXT-03`.
6. El servicio devuelve el resultado de entrega.
7. El sistema registra el resultado.
8. El sistema actualiza el estado de notificación.
9. Finaliza el caso de uso.

## 7. Flujos alternos

### FA-01 — Notificación en dashboard

El sistema publica la alerta en el dashboard como canal interno y registra su disponibilidad.

### FA-02 — Múltiples destinatarios

El sistema envía la notificación a cada destinatario autorizado y conserva el resultado individual.

### FA-03 — Reintento autorizado

El sistema reintenta la entrega según la política configurada, sin duplicar indefinidamente la notificación.

### FA-04 — Escalamiento

Si el canal principal falla, el sistema registra o activa el canal alterno autorizado.

## 8. Flujos de excepción

### FE-01 — Destinatario no configurado

El sistema registra la alerta como pendiente y notifica al administrador responsable.

### FE-02 — Servicio externo no disponible

El sistema registra la indisponibilidad y conserva la alerta para reintento o revisión.

### FE-03 — Contenido inválido

El sistema impide el envío y registra el error de plantilla o datos.

### FE-04 — Duplicado

El sistema identifica una notificación ya enviada para la misma alerta, evento y destinatario, según la clave de idempotencia.

## 9. Reglas provisionales

- `RN-CU16-01`: solo las condiciones que cumplen reglas aprobadas generan notificación crítica.
- `RN-CU16-02`: cada notificación debe ser idempotente.
- `RN-CU16-03`: un fallo de entrega no elimina la alerta.
- `RN-CU16-04`: no se incluyen datos sensibles innecesarios.
- `RN-CU16-05`: la entrega debe conservar evidencia técnica suficiente.
- `RN-CU16-06`: una notificación enviada no equivale a una alerta atendida.

## 10. Requisitos relacionados

- `RF-15` Notificar condiciones críticas mediante canales autorizados.
- `RNF-16` Entregar o registrar la notificación dentro del tiempo aprobado `[PENDIENTE DE MEDICIÓN]`.
- `RN-16` Mantener idempotencia y auditoría.

## 11. Escenarios candidatos

- `ESC-CU16-01` Notificación crítica entregada.
- `ESC-CU16-02` Notificación visible en dashboard.
- `ESC-CU16-03` Servicio externo no disponible.
- `ESC-CU16-04` Reintento sin duplicación.
- `ESC-CU16-05` Destinatario no configurado.

## 12. Criterios de aceptación preliminares

- Solo se notifican condiciones críticas aprobadas.
- El contenido referencia una alerta existente.
- Se registra el resultado por destinatario y canal.
- Los fallos no eliminan la alerta.
- Los reintentos son controlados e idempotentes.
- La notificación no se presenta como acción atendida.
