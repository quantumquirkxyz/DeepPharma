# CU-03 — Generar predicciones de riesgo de desabastecimiento

**Versión:** 0.1
**Estado:** Borrador en refinamiento
**Clasificación:** Caso de uso funcional principal
**Fuente académica:** `SRC-01`, `SRC-05`, `SRC-07`, `SRC-08`

## 1. Objetivo

Generar predicciones reproducibles sobre el riesgo futuro de desabastecimiento utilizando un modelo aprobado y datos de inventario disponibles para un horizonte definido.

El resultado de este caso de uso es una predicción. La clasificación operativa de alertas se realiza mediante reglas y criterios de negocio explícitos, no se confunde con la salida directa del modelo.

## 2. Actores

- **Actor principal:** DeepPharma mediante ejecución programada interna.
- **Actor secundario:** `ACT-01 Administrador del sistema`, `ACT-02 Farmacéutico` o `ACT-03 Ingeniero de Machine Learning`, según autorización para ejecución bajo demanda.
- **Servicios relacionados:** persistencia de predicciones y servicio de notificaciones.

La ejecución programada no se representa como actor externo.

## 3. Disparadores

- Ejecución programada por la política operativa.
- Solicitud manual de un actor autorizado.

Ambos disparadores utilizan el mismo caso de uso.

## 4. Precondiciones

- Existe un modelo aprobado y habilitado para inferencia.
- El modelo tiene versión y metadatos registrados.
- Existen datos de inventario aptos para inferencia.
- El horizonte predictivo está definido.
- Las reglas de clasificación operativa están disponibles o se puede marcar el resultado como pendiente.

## 5. Postcondiciones

### Éxito

- Se registra una ejecución de inferencia.
- Se generan predicciones para las entidades procesadas.
- Cada predicción conserva modelo, versión, fecha, datos de entrada y horizonte.
- Se calcula la clasificación operativa cuando existen reglas vigentes.
- Las predicciones quedan disponibles para `CU-04`.
- Las condiciones críticas pueden activar `CU-16`.

### Fallo

- La ejecución queda registrada como fallida o incompleta.
- No se presentan resultados parciales como resultados completos.
- Se informa la causa y el alcance del fallo.
- Las predicciones anteriores no se sobrescriben sin una ejecución válida.

## 6. Flujo básico

1. DeepPharma inicia la ejecución programada o un actor autorizado solicita una ejecución.
2. El sistema identifica el modelo aprobado vigente.
3. El sistema obtiene los datos de inventario y variables requeridas.
4. El sistema verifica la vigencia, completitud y compatibilidad de los datos.
5. El sistema registra la ejecución de inferencia.
6. El sistema ejecuta el modelo sobre los datos seleccionados.
7. El sistema calcula la salida predictiva.
8. El sistema calcula días de cobertura y variables operativas cuando sea posible.
9. El sistema aplica las reglas de clasificación operativa aprobadas.
10. El sistema almacena la predicción, sus razones y su trazabilidad.
11. El sistema identifica condiciones que pueden producir alertas.
12. El sistema actualiza la disponibilidad de resultados para `CU-04`.
13. Finaliza el caso de uso.

## 7. Flujos alternos

### FA-01 — Ejecución bajo demanda

Se origina en el paso 1.

1. El actor solicita una ejecución.
2. El sistema verifica permisos y parámetros.
3. El sistema continúa en el paso 2 del flujo básico.

### FA-02 — Procesar un subconjunto

Se origina en el paso 3.

1. El actor autorizado selecciona un centro, medicamento o período.
2. El sistema valida el alcance.
3. El sistema registra el subconjunto procesado.
4. Continúa en el paso 5 del flujo básico.

### FA-03 — Resultado sin clasificación operativa

Se origina en el paso 9.

1. El sistema conserva la predicción del modelo.
2. El sistema marca la clasificación operativa como `indeterminada`.
3. Registra la razón de la indeterminación.
4. Continúa en el paso 10 del flujo básico.

## 8. Flujos de excepción

### FE-01 — No existe modelo aprobado

1. El sistema no inicia la inferencia.
2. Registra la ejecución como bloqueada.
3. Informa que se requiere un modelo aprobado mediante `CU-02`.

### FE-02 — Datos insuficientes

1. El sistema identifica los datos faltantes o inválidos.
2. Marca las entidades afectadas como no evaluables.
3. No convierte la ausencia de datos en riesgo cero.
4. Registra el alcance y el motivo.

### FE-03 — Modelo incompatible

1. El sistema detecta que el esquema de entrada no corresponde a la versión del modelo.
2. Rechaza la ejecución.
3. Registra el conflicto de versiones.

### FE-04 — Error durante la inferencia

1. El sistema registra el error técnico.
2. Marca la ejecución como fallida o parcial.
3. No publica el resultado como completo.
4. Informa a los actores responsables.

### FE-05 — Resultado fuera de rango

1. El sistema detecta una probabilidad, cantidad o clasificación inválida.
2. No publica la salida afectada como confiable.
3. Registra el defecto de datos, modelo o configuración.

## 9. Reglas de negocio provisionales

- `RN-CU03-01`: solo se utilizan modelos aprobados.
- `RN-CU03-02`: cada predicción debe conservar la versión del modelo utilizado.
- `RN-CU03-03`: predicción de ML y nivel de alerta operativa son valores distintos.
- `RN-CU03-04`: una ausencia de datos no se interpreta automáticamente como ausencia de riesgo.
- `RN-CU03-05`: el horizonte inicial de predicción es de 30 días, sujeto a validación.
- `RN-CU03-06`: los umbrales de 10 y 20 días son hipótesis `HIP-01` y `HIP-02`, no reglas aprobadas.
- `RN-CU03-07`: una ejecución fallida no reemplaza la última predicción válida.
- `RN-CU03-08`: reutilizar la última predicción válida debe mostrar su antigüedad y estado desactualizado.

## 10. Requisitos relacionados

- `RF-03` Generar predicciones de riesgo con horizonte definido.
- `RNF-03` Completar una ejecución dentro del tiempo aprobado `[PENDIENTE DE MEDICIÓN]`.
- `RN-03` Mantener trazabilidad de modelo, datos y ejecución.

## 11. Escenarios candidatos

- `ESC-CU03-01` Generación programada exitosa.
- `ESC-CU03-02` Ejecución manual autorizada.
- `ESC-CU03-03` Datos insuficientes para una entidad.
- `ESC-CU03-04` Ausencia de modelo aprobado.
- `ESC-CU03-05` Fallo de inferencia con predicción anterior disponible.

## 12. Criterios de aceptación preliminares

- La ejecución programada y manual utilizan el mismo caso de uso.
- Solo se usa un modelo aprobado.
- Cada predicción es reproducible y trazable.
- Se distingue la salida del modelo de la alerta operativa.
- Los datos faltantes generan estado indeterminado, no riesgo cero.
- Las ejecuciones fallidas no se presentan como completas.
- Una predicción anterior se identifica explícitamente como desactualizada.
