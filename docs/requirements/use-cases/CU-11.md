# CU-11 — Registrar modelo aprobado

**Versión:** 0.1
**Estado:** Borrador en refinamiento
**Clasificación:** Caso de uso funcional candidato
**Fuente:** `CU-02`, `CU-10`, `SRC-11`, prácticas de gestión de modelos

## 1. Objetivo

Permitir que un modelo evaluado sea revisado, aprobado y registrado como versión habilitada para inferencia, conservando evidencia, responsable y condiciones de uso.

## 2. Actores

- **Actor principal:** `ACT-03 Ingeniero de Machine Learning`.
- **Actor secundario:** `ACT-01 Administrador del sistema`.

## 3. Disparador

El ingeniero solicita registrar un modelo que cumple los criterios de evaluación aprobados.

## 4. Precondiciones

- Existe un modelo entrenado y evaluado.
- Existe un reporte reproducible.
- Las métricas cumplen o documentan los criterios aplicables.
- La versión del modelo y del dataset están identificadas.
- El actor tiene permiso para solicitar o aprobar la promoción.

## 5. Postcondiciones

### Éxito

- El modelo queda registrado con una versión única.
- Se almacena su metadata y reporte.
- Se define su estado: `aprobado`, `habilitado`, `retirado` u otro estado controlado.
- `CU-03` puede utilizarlo si está habilitado para inferencia.

### Rechazo

- El modelo conserva su registro como no aprobado.
- Se documentan razones y condiciones faltantes.
- El modelo no se utiliza para inferencia operativa.

## 6. Flujo básico

1. El ingeniero selecciona un modelo evaluado.
2. El sistema muestra métricas, dataset, versión y limitaciones.
3. El ingeniero solicita la aprobación.
4. El sistema verifica criterios obligatorios.
5. El sistema registra responsable, fecha y decisión.
6. El sistema asigna una versión del modelo.
7. El sistema cambia el estado a `aprobado` o `habilitado` según autorización.
8. El sistema informa el resultado.
9. Finaliza el caso de uso.

## 7. Flujos alternos

### FA-01 — Revisión administrativa

El administrador revisa metadata, permisos y condiciones operativas antes de habilitar el modelo.

### FA-02 — Retirar modelo vigente

Un actor autorizado retira un modelo. El sistema conserva su historial y evita nuevas inferencias con esa versión.

### FA-03 — Reemplazar modelo vigente

El sistema registra el nuevo modelo y conserva la relación con la versión anterior, sin borrar su historial.

## 8. Flujos de excepción

### FE-01 — Reporte incompleto

El sistema bloquea la aprobación y muestra los elementos faltantes.

### FE-02 — Métricas insuficientes

El sistema rechaza la promoción o la deja pendiente de decisión explícita, sin habilitar automáticamente el modelo.

### FE-03 — Versión duplicada

El sistema rechaza el registro o crea una versión inequívoca sin sobrescribir la existente.

### FE-04 — Conflicto de aprobación

El sistema impide que dos decisiones incompatibles habiliten modelos simultáneamente sin una política definida.

## 9. Reglas provisionales

- `RN-CU11-01`: un modelo entrenado no es automáticamente un modelo aprobado.
- `RN-CU11-02`: cada versión debe ser inmutable una vez habilitada.
- `RN-CU11-03`: retirar un modelo no elimina sus reportes ni predicciones históricas.
- `RN-CU11-04`: debe existir un modelo habilitado o una política explícita de indisponibilidad.
- `RN-CU11-05`: la aprobación conserva responsable, fecha, evidencia y limitaciones.
- `RN-CU11-06`: una nueva versión no debe invalidar silenciosamente resultados históricos.

## 10. Requisitos relacionados

- `RF-11` Registrar el ciclo de vida de modelos aprobados.
- `RNF-11` Reproducibilidad y auditabilidad de modelos.
- `RN-11` Promoción controlada de modelos.

## 11. Escenarios candidatos

- `ESC-CU11-01` Aprobar un modelo evaluado.
- `ESC-CU11-02` Rechazar un modelo con reporte incompleto.
- `ESC-CU11-03` Retirar modelo vigente.
- `ESC-CU11-04` Reemplazar modelo sin eliminar historial.

## 12. Criterios de aceptación preliminares

- No se habilita un modelo sin evaluación registrada.
- La versión y metadata son trazables.
- La decisión de aprobación tiene responsable y fecha.
- Las versiones retiradas conservan historial.
- Una nueva versión no borra ni altera resultados anteriores.

## 13. Pendientes

- Definir política de rollback.
- Definir si puede existir más de un modelo habilitado.
